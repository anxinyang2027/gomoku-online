## 一、本文目标与边界

**目标(一句话):把"能跑的课程作业",升级成"有服务端权威对局、有电脑 AI、有排位成长、能联机、可交付部署"的完整作品。**

1. **不重构前端框架**——原生 HTML/CSS/JS 继续用,只做模块内改造(见 J6 决策 D10)。
2. **不动已冻结的 6 张表与既有接口形状**——只加列、只加新表、只加新接口。
3. **不做禁手规则、不做对称坐标存储、不做 i18n**——范围优先级不在这。
4. 金币不接充值/支付,商城维持外观道具体系。

## 四、七期 · 服务端对局引擎 + 电脑 AI(J6–J12)

这是"简陋"体感最直接的升级:让**后端自己也会下棋**,对局由服务器裁决。

### J6 设计决策 `- [x]` 2026-10-23 落地;D10 仅做了 game.js 分支,board.js 抽模块顺延到八期
- **决策 D8(AI 挂服务端,不做前端 AI)**:三难度 AI 跑在 JVM 里,复用 `Referee`;前端只报落子、收结果,反作弊一举两得——AI 对局的胜负从头到尾由服务端生成。
- **决策 D9(会话内存 + 每步落库)**:`game_session` 进行中对局在内存 `ConcurrentHashMap` 中活跃,每一步同步写 moves JSON 落库;JVM 重启后"playing"未完成的会话自动标记"系统中止",不计分。课程/校园场景单实例部署,不引入 Redis。
- **决策 D10(前端不引框架,走 ES Module)**:`board.js` 抽成可 import 的纯渲染模块,game 页复用;触控/复盘不动。

### J7 `game_session` 新表(DDL 增量①) `- [x]` init.sql 已加表;存量库执行 `db\bot-session-upgrade.sql`

```sql
CREATE TABLE game_session (
  id          BIGINT PRIMARY KEY AUTO_INCREMENT,
  mode        VARCHAR(16)  NOT NULL COMMENT 'bot / online',
  difficulty  TINYINT      NULL COMMENT 'bot:1/2/3',
  owner_id    BIGINT       NOT NULL,
  black_id    BIGINT       NULL, white_id BIGINT NULL,   -- bot 时 robot 一侧 NULL
  status      VARCHAR(16)  NOT NULL DEFAULT 'playing' COMMENT 'playing/finished/aborted',
  turn_color  TINYINT      NOT NULL DEFAULT 1,
  moves_json  JSON         NULL,
  winner_color TINYINT     NULL, result TINYINT NULL, end_reason VARCHAR(16) NULL,
  created_at  DATETIME DEFAULT CURRENT_TIMESTAMP,
  updated_at  DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  INDEX idx_status(mode,status), INDEX idx_user(owner_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```
既有 6 张表与契约不动,此为纯增量;`game_record` 继续充当"对局完单据",会话结算时生成一行(mode=bot)。

### J8 AI 引擎(核心算法) `- [x]` `game\ai\BotEngine.java`;BotEngineTest 7 用例全绿(堵四/成五/时限 ≤2s)
`game/ai/BotDifficulty.java` + `game/ai/BotEngine.java`:
- 选点统一:候选点 = 已落子 ±2 范围内的空位;棋型分(活四 10000/冲四 1000/双活三 1200/活三 800/活二 60 等,与经典开源五子棋评分体系同源)。
- **难度1(入门)**:启发式贪心,能堵四连、能成五连,深度 0;偶尔失误但不失大格。
- **难度2(进阶)**:α-β 极小极大,深度 2,活四/必杀点优先进入搜索;
- **难度3(高手)**:α-β 深度 4,仅评分前 6 的候选点进入搜索;最劣单步 ≤2s(有专项计时用例)。
- 复用 `Referee.judge` 终局判定,禁止重复落子与越界。
- **验收**:随机局面快照脚本生成 gold 文本,难度 2/3 回归零漂移;单步计算 ≤2s 用单元测卡住。

## 六、九期 · 联机对战 WebSocket(J18–J23)

> 承接原计划 H6,本节给出更细的协议与状态机。

### J18 基础设施 `- [ ]`
`spring-boot-starter-websocket`,端点 `/ws/gomoku`;握手之前校验 JWT(无效直接 close);在线连接表(内存)支持"一个账号多端登录以最新为准"。

### J19 匹配与房间状态机 `- [ ]`
| 消息帧 | client → server | server → client |
|---|---|---|
| 入队 | `{type:"queue_join"}` | `{type:"queued", pos}` / `{type:"matched", sessionId, opponent:{name,elo,avatar}}` |
| 落子 | `{type:"move", sessionId, seq, r, c}` | `{type:"board", seq, last:{r,c,color,ts}, turn}`(服务器按 seq 拒绝乱序/重放) |
| 终局 | 认输/求和 | `{type:"result", winnerColor, endReason}` → 服务端统一结算 Elo → `game_record(mode=online)` |

- 状态机:`IDLE → QUEUE(5s 内凑不齐就继续等待)→ PLAYING(每步限时 45s 超时判负;断线 >30s 托管自动落子并保留快照,回线即重发 `board`)→ RESULT`。
- 权威性:以房间为中心单点受理,每手只认最新 seq;重放/双击/换方一律拒绝(裁决复用七期引擎)。

### J20 前端联机页 `- [ ]`
新 `online.html`(或 game 页加联机 tab):排队等待 → 对局 → 实时战报;断线重连自动 `GET /api/game/{id}` 恢复盘面。

### J21 联机结算整合 `- [ ]`

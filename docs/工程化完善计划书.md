## 一、K1：WebSocket 实时推送（在线对战）

### 设计

- **传输**：原生 WebSocket（`spring-boot-starter-websocket`），端点 `/ws/online`，
  连接时带 token 鉴权（复用 JwtUtil，URL 查询参数 `?token=`）。
- **协议**（JSON 双向）：
  - 客户端 → 服务端：`{type:"sub", gameId}` 订阅对局；`{type:"unsub"}` 退订
  - 服务端 → 客户端：`{type:"snapshot", data:OnlineSnapshotResp}`（与 HTTP 快照同形）
- **混合策略**（关键决策 D10）：
  - **写操作仍走 HTTP**（落子/认输/求和/拒绝）——复用现有接口、拦截器鉴权、参数校验
  - **WebSocket 只做推送**——任何状态变化（对方落子、托管、终局、求和请求）后，
    服务端向该局两名订阅者广播最新快照
  - 前端：有 WS 连接时不再轮询；WS 断线自动降级回 1.5s 轮询（网络差/代理环境兜底）
- **为什么不上 STOMP**：单广播场景不值得引入子协议；原生 handler 60 行内解决，
  答辩讲"取舍"比讲"堆技术"加分。

### 验收

- 双开浏览器对局：一方落子，另一方 <100ms 内看到（原来 1.5s）
- 杀掉 WS 连接（断网模拟）：前端自动回轮询，对局不中断
- HTTP 接口全部不受影响（旧客户端照常工作）

## 二、K2：状态持久化

### K2a：重启续局验证（纯测试，零代码预期）

game_session 每步落库已实现。补一个集成测试：开局→落 5 手→重启服务（重建
OnlineGameService 实例）→ 验证 `findActiveByUser` 能从库重建会话、双方可继续落子。
若失败则修 rebuild 链路。

### K2b：Redis 托管匹配池/房间（可选，默认不做）

匹配池/房间的丢失代价 = 重新排队一次，可接受。引入 Redis 的收益（多实例扩容）
在课程作业场景不成立，反而增加部署依赖。**决策 D11：不引入 Redis**，
在答辩口径中明说"单实例内存态 + 落库对局快照，重启后对局可续、排队需重排，
是场景化的取舍而非疏漏"。

## 四、K4：配置分离 + Docker + CI

### K4a：Profile 三环境

- `application.yml`（公共）→ `application-dev.yml` / `application-prod.yml`
- JWT secret：dev 固定值；prod 从环境变量 `GOMOKU_JWT_SECRET` 读，缺失则启动失败
- DB 连接同样走环境变量（`SPRING_DATASOURCE_URL/USERNAME/PASSWORD`）

### K4b：Docker

- `Dockerfile`：多阶段构建（maven 打包 → JRE17 运行），前端 dist 已在 static 内
- `docker-compose.yml`：mysql:8 + gomoku 后端，健康检查 + 依赖顺序 + 自动建库
- `.dockerignore`

### K4c：GitHub Actions CI

`.github/workflows/ci.yml`：push/PR 触发 →
1. 前端：npm ci && npm run build
2. 后端：mvn test（H2 内存库跑单测，不依赖外部 MySQL）
3. mvn package（打 jar 不部署）
